# Trusted SQLite migrations

The SS01 greenfield baseline is schema **2 / 18 domain tables**:

- `0000_baseline.sql` is generated by pinned Drizzle Kit 0.31.11 from
  `src/lib/server/db/schema.ts`. Account has required username/email; there is no
  setup-token table, title field or role model.
- `0001_guards_and_search.sql` contains the reviewed note identity/revision,
  ready-reference and reference-safe cleanup triggers plus the FTS5 trigram table.
  Drizzle snapshots describe tables/indexes/checks, not these custom objects.
- The version-2 `rebuild-search-v1` data step backfills derived fields with the exact
  application NFKC/lowercase normalizer. Fresh databases are empty; known schema-1
  staging can contain notes. Literal separate-field predicates remain authoritative.
  No virtual-table write triggers or `trusted_schema=ON` are needed.

Container, dev and built start all run the shared initializer before serving:
restore recovery → keys → SQL/data migration/pre-upgrade wrapper → settings.
Browser two-step account setup and format-v2 backup/restore are implemented. No
operator migration command or request-time migration. Actual application gates and
the SS01 directory-exchange clarification: `docs/simplify-setup/PROGRESS.md`.

## Adding a migration

- Tables: `npm run db:generate -- --name=<name>`.
- Custom SQL: `npm run db:generate -- --custom --name=<name>`.
- Review SQL/snapshots/`meta/_journal.json` together and update `SCHEMA_VERSION` in
  `src/lib/server/db/migrations.ts`. Never edit already-applied SQL.
- Optional data step: add a stable `{name, run(db, {now})}` under the schema version
  in `src/lib/server/db/data-migrations.ts`. Database-only, synchronous, bounded,
  deterministic; no filesystem/network/independent clock reads. Changing an applied
  step implementation needs a new migration, not reuse of its name.
- Never schema-push, migrate in a request, execute archive-supplied SQL or run a
  second application writer on the same data tree.

## Runner and ledger

The application owns contiguous SHA-256-checked `__pandanote_migrations` plus SQLite
`user_version` (journal index + 1). Hashes normalize CRLF to LF. Nullable `data_step`
records each registered function's identity. SQL then data step for every pending
version, ledger writes, integrity/FK checks and user version commit in **one IMMEDIATE
transaction**, sharing one fixed timestamp. Failure rolls back everything and prints
only the migration number/name, never the underlying SQL/data-step exception.

Old `0000_foundation` histories and ledgers without data-step identity are pre-release
and refused with the approved move-away/start-empty message. There is no retrofit or
pre-release data migration. Unknown databases, modified SQL/step history and newer
schemas are also refused. Migrations are forward-only; failure rollback is not a
destructive down-migration feature.

The approved no-drafts change intentionally replaced the fresh-install baseline
without an importer or upgrade for earlier development data. Those folders/archives
fail trust even though their numeric schema version can still be 2. A SQL hash or
data-step mismatch reports safe recovery instructions: use the matching build for
old data, or stop the app and select a new unused private folder (`DATA_DIR` locally,
`DATA_PATH` in Compose) for fresh setup. Preserve the whole old folder, including keys,
files and SQLite sidecars; never rewrite the ledger to bypass compatibility checks.
See [local startup troubleshooting](../README.md#startup-fails-with-applied-migration-history-does-not-match).

## Live pre-upgrade copy and staged restore

The shared container/dev/built startup uses `upgradeDatabase` before applying
pending migrations. Fresh/current databases skip capture. The wrapper uses SQLite online
backup (including WAL), checks page-count × 1.1 + manifest space + disk reserve,
fsyncs a private self-contained DELETE-mode DB and manifest with from/to schema,
immutable upgrading-app version and timestamp. Key material is never copied.

Portable Node cannot exchange nonempty directories in one atomic rename. The first
implementation uses durable journaled rotation: retain `pre-upgrade.old/`, publish
`pre-upgrade/`, record installation, then remove old state. Interrupted rotation is
recovered before any next upgrade. It is crash-safe but **not a single atomic
exchange**; this literal specification clarification remains open before SS01's
full gate can close. Upgrade paths and journal are known private storage paths.

The DB-only runner is also used on isolated, validated staging without creating a
live pre-upgrade copy. The untrusted archive's exact SQL object/ledger inventory must
be validated before migration; a matching version alone is never enough. Format-v2
archive trust validates exact known baseline-v1/v2 objects/ledger, migrates v1 only
on disposable staging with SQL/data steps, rebuilds trusted FTS and reinspects.
Format-1 pre-release archives are refused before extraction.

`Persistence` opens only the current trusted history and never migrates during a
request. `npm run search:reindex` remains stopped-app-only and changes derived search,
never source bodies, revisions, attachments or receipts. Container equivalent:
stop pandanote → `docker compose run --rm pandanote reindex` → start pandanote.
Interactive `npm run reset-password` is separately live-safe; it does not initialize,
migrate or recover journals. Immediate copy rollback instructions and their DB-only
limitations are in [the deployment guide](../ops/DEPLOYMENT.md#6-roll-back-an-upgrade).
